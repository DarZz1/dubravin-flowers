# DUBRAVIN&FLOWERS — сайт-витрина + CMS

Цветочный магазин в Кирове. Чистый HTML/CSS/JS без фреймворков и сборки.
Сайт разбит на модули по папкам; панель управления (CMS) доступна по адресу **`/admin`**
и защищена паролем.

CMS работает в двух режимах, которые переключаются автоматически:

| Режим | Когда | Где живут правки | Авторизация |
|---|---|---|---|
| **Серверный** | запущен `backend/` (VPS) или Netlify Functions | VPS: БД-файл + фото в `img/`. Netlify: Netlify Blobs (постоянное хранилище) | логин и хэш scrypt — **на бэкенде**, клиент получает только токен сессии |
| **Клиентский** | статический хостинг без API | `localStorage` браузера, публикация вручную через `data.json` | локальный PBKDF2 (как было раньше) |

Витрина определяет режим одним запросом `GET /api/health`. Без сервера сайт
работает полностью — ничего не ломается.

## Быстрый старт

**Вариант 1 — только витрина (статика, клиентская CMS):**

```bash
npm install          # jsdom для тестов
npm run serve        # http://localhost:8080
```

**Вариант 2 — витрина + серверная CMS (рекомендуется для разработки):**

```bash
npm install                                    # jsdom + busboy
npm run backend:seed                           # стартовый каталог → backend/seed.json
node backend/cli/admin.js create --random      # создаёт админа и печатает пароль ОДИН раз
npm run server                                 # http://127.0.0.1:8090
```

- Витрина: `http://127.0.0.1:8090/`
- Панель управления: `http://127.0.0.1:8090/admin` (появятся поля «Логин» и «Пароль»)
- API: `http://127.0.0.1:8090/api/health`

Полезные команды:

```bash
npm test                    # 321 тест: витрина + backend + Netlify + QA
npm run test:qa             # только адаптив, производительность, сценарии CMS
npm run backend:doctor      # диагностика: конфиг, scrypt, целостность медиа
npm run admin:recovery      # одноразовый токен восстановления пароля
npm run audit               # последние записи журнала безопасности
node tools/pack.js netlify  # архив для деплоя (или npm run pack:netlify)
npm run server &            # стенд должен быть поднят
python3 tools/demo-check.py # сквозная проверка CMS на живом сервере
```

Альтернатива без Node: `python3 -m http.server 8080` в корне проекта
(серверной CMS при этом не будет — сайт перейдёт в клиентский режим).

> Важно: открывать сайт двойным кликом по `index.html` (протокол `file://`) не
> рекомендуется — загрузка `data.json`, адрес `/admin` и часть браузерных API
> (WebCrypto) работают только при раздаче по HTTP.

## Панель управления (`/admin`)

1. Откройте `https://ваш-домен/admin` (локально — `http://localhost:8080/admin`).
2. **Первый запуск:** сразу показывается форма авторизации. Экран «придумайте
   пароль» убран — учётные данные создаются автоматически при первом открытии
   страницы. Пароль по умолчанию: **`dubravin`** (константа
   `DF_DEFAULT_PASSWORD` в `assets/js/admin/admin-main.js`). Смените его
   в первой же сессии: **Данные → Безопасность**. Хэш — PBKDF2-HMAC-SHA256
   (260 000 итераций + случайная соль). Сброс: очистить данные сайта в
   настройках браузера — пароль вернётся к значению по умолчанию.
3. **Дальше:** вход по паролю, после успешной проверки открывается панель.
   После 5 неудач — блокировка на 30 секунд
   с удвоением при каждой следующей неудаче (потолок 15 минут).
   Сессия истекает через 30 минут бездействия; кнопка «Выйти» — в шапке.
4. Вкладки: **Hero** (главное фото), **Подборки** (категории),
   **Товары** (добавление/редактирование/удаление, фото, цены, состав),
   **Данные** (экспорт/импорт `data.json`, сброс, **смена пароля**).

### Где хранятся изменения

- Все правки сохраняются **локально в браузере** (localStorage, ключ `df-cms-v1`)
  и мгновенно применяются на сайте: открытые вкладки витрины обновляются
  автоматически (событие `storage`).
- Изменения видит только ваш браузер. Чтобы **опубликовать их для всех
  посетителей**: вкладка «Данные» → «Скачать data.json» → загрузите файл
  в корень сайта рядом с `index.html` (через файловый менеджер хостинга).
  После этого каждый новый посетитель получит обновлённый каталог.
- Фото, загруженные через CMS, сжимаются до 1200 px и хранятся в том же
  localStorage (учтите лимит браузера ~5 МБ). Для больших объёмов кладите
  файлы в папку `img/<ID товара>/1.jpg` — сайт подхватит их автоматически.

## Публикация на хостинге

| Хостинг          | Что сделать                                                                 |
|------------------|------------------------------------------------------------------------------|
| Netlify          | залить папку как есть — `_headers`, `_redirects`, `netlify.toml` сработают сами |
| Cloudflare Pages | залить папку как есть — `_headers` и `_redirects` сработают                    |
| Vercel           | залить папку как есть — `vercel.json` сработает                                |
| GitHub Pages     | залить папку (без `tests/`, `deploy/`, `node_modules/`); заголовки — только из meta-CSP |
| Apache           | `.htaccess` уже в корне                                                        |
| nginx            | взять `deploy/nginx.conf.example`, вписать домен и пути                        |

**Не публикуйте** каталоги `tests/`, `deploy/`, `build_tools/`, `node_modules/`
и файлы `package*.json` (локальный сервер и конфиги хостингов их всё равно
блокируют, но лучше не загружать их вовсе).

## Тесты

```bash
npm install
npm test              # 321 тест: витрина + серверный слой + Netlify + QA
npm run test:site     # 183 — витрина и клиентская CMS
npm run test:backend  #  96 — API, авторизация, медиа, OWASP, интеграция
npm run test:qa       #  28 — адаптив, производительность, сценарии CMS
npm run test:all      #  то же последовательно (без параллелизма файлов)
```

**Витрина и клиентская CMS** (`tests/`): `structure` (целостность проекта и
ссылок), `store` (БД и санитизация), `templates` (шаблоны и XSS-экранирование),
`router` (маршруты, `#/admin` → 404), `auth` (PBKDF2/SHA-256 сверяются с эталоном
`node:crypto`, блокировки, сессии), `admin-panel` (CMS в реальном DOM: вход,
CRUD, экспорт/импорт), `site-dom` (витрина целиком: тема, меню, cookie, заказ в
VK, живая синхронизация), `gallery-fallback` (заглушки и перебор расширений),
`serve` (HTTP: маршруты, 404, path traversal, заголовки),
`security-static` (статический аудит всех исходников).

**Серверный слой** (`tests/backend/`): тесты поднимают **настоящий сервер**
(`backend/server/server.js`) на свободном порту в изолированных временных
каталогах и ходят в него реальными HTTP-запросами.

| Набор | Что проверяет |
|---|---|
| `auth-api` | вход, httpOnly-кука, CSRF (Bearer и double-submit), `me`, logout, блокировка перебора, смена пароля с отзывом сессий, восстановление по одноразовому токену, отсутствие секретов в журнале |
| `content-api` | CRUD товаров и подборок, hero, лимиты, XSS в данных, `javascript:`-URL, prototype pollution, ревизии `If-Match` → 409, импорт, сброс, публикация `data.json` |
| `media-api` | загрузка фото, **удаление старых файлов при замене**, удаление медиа вместе с товаром, проверка по сигнатуре и структуре файла, лимиты, traversal в именах и id, раздача `/img/`, очистка «осиротевших» |
| `security-owasp` | 34 проверки по категориям A01–A09 (см. SECURITY-AUDIT.md) |
| `cms-integration` | боевой клиентский код (`store.js`, `admin/*.js`) против живого сервера: витрина берёт каталог из API, правка в CMS публикуется, без токена запись не проходит, витрина работает и без сервера |

**QA** (`tests/qa/`): `responsive-performance` (viewport, брейкпоинты 320…1400+,
фиксированные ширины, тач-цели по WCAG 2.5.8/2.5.5, горизонтальный скролл, вес
страницы, gzip, TTFB, кэш, блокирующие ресурсы, неблокирующая загрузка шрифтов)
и `cms-scenarios` (10 сквозных сценариев «админ сделал → посетитель увидел»,
включая рендер витрины боевым кодом в jsdom).

Ручные сценарии, которые нельзя автоматизировать без браузера (LCP/CLS/INP,
кросс-браузерность, доступность), описаны в [QA-PLAN.md](QA-PLAN.md).

## Безопасность

**Клиентская часть** (как было): строгая CSP без inline-скриптов, экранирование
всех данных из БД через `esc()`, белые списки URL изображений (`safeUrl()`),
локальный PBKDF2 для клиентского режима, блокировка перебора, короткие сессии,
`noindex` для `/admin`, серверные заголовки для всех хостингов. Модель угроз и
её честные ограничения — в [SECURITY.md](SECURITY.md).

**Серверный слой** (добавлено): пароль проверяется **только на бэкенде** —
scrypt N=2¹⁷ со случайной солью, сравнение `timingSafeEqual`, хэш никогда не
покидает сервер. Токен сессии — 32 байта CSPRNG, в БД хранится лишь его
HMAC-хэш, клиенту отдаётся в httpOnly-куке (`Secure`, `SameSite=Strict`,
`__Host-` на HTTPS) и в памяти вкладки. CSRF закрыт тремя рубежами: SameSite,
обязательный кастомный заголовок (`Authorization: Bearer` или `X-CSRF-Token`),
отсутствие CORS по умолчанию. Блокировка перебора: 5 неудач → 30 с с удвоением,
потолок 15 минут, плюс отдельный лимит по IP. Загружаемые изображения
проверяются по сигнатуре **и** структуре файла, имена генерирует сервер,
path traversal закрыт на двух уровнях. Запись БД атомарна (tmp → fsync →
rename), все мутации идут через одну очередь. Журнал безопасности пишет события
без паролей, токенов и хэшей.

Подробный аудит по OWASP Top 10 с перечнем найденных и закрытых дефектов —
в [SECURITY-AUDIT.md](SECURITY-AUDIT.md).

Восстановление доступа (пароль утерян):

```bash
node backend/cli/admin.js recovery --login <логин>   # одноразовый токен на 15 минут
# далее: POST /api/auth/reset { "token": "...", "newPassword": "..." }
node backend/cli/admin.js passwd --login <логин> --random   # или сразу новый пароль
node backend/cli/admin.js unlock --login <логин>            # снять блокировку перебора
```
