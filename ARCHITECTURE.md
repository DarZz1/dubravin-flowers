# ARCHITECTURE.md — архитектура проекта после перевода CMS на сервер

## 1. Зачем понадобился серверный слой

Исходный сайт — полностью статический: HTML/CSS/JS, а «панель управления» хранила
правки в `localStorage` одного посетителя и публиковала их для всех только
вручную (скачать `data.json` → залить на хостинг). Это давало три ограничения:

1. правки не видны другим людям и другим устройствам;
2. медиафайлы жили в `localStorage` с лимитом ~5 МБ на весь сайт;
3. пароль проверялся в браузере, то есть криптостойкой границы не было вовсе
   (это честно описано в SECURITY.md, раздел 2).

Серверный слой снимает все три: контент и фото хранятся на сервере, пароль
сверяется с хэшем scrypt на бэкенде, а публикация происходит автоматически.

## 2. Два режима работы — один и тот же код

```
                       ┌─────────────────────────────────────────┐
                       │  assets/js/*  (витрина и CMS-панель)    │
                       │  один и тот же клиентский код           │
                       └───────────────┬─────────────────────────┘
                                       │
                    dfProbeServer() → GET /api/health
                                       │
                 ┌─────────────────────┴──────────────────────┐
          сервер есть                                   сервера нет
                 │                                             │
   ┌─────────────▼──────────────┐              ┌───────────────▼───────────────┐
   │ СЕРВЕРНЫЙ РЕЖИМ            │              │ СТАТИЧЕСКИЙ РЕЖИМ             │
   │ • вход → POST /api/auth/   │              │ • вход → локальный DFAuth     │
   │   login (scrypt на бэке)   │              │   (PBKDF2 в WebCrypto)        │
   │ • токен в памяти вкладки + │              │ • правки в localStorage       │
   │   httpOnly-кука            │              │   (ключ df-cms-v1)            │
   │ • dbSave() → PUT /api/     │              │ • публикация вручную:         │
   │   admin/content            │              │   «Скачать data.json» →       │
   │ • фото → multipart на диск │              │   залить в корень сайта       │
   │ • сервер пишет data.json   │              │                               │
   └────────────────────────────┘              └───────────────────────────────┘
```

Переключение автоматическое: `store.js` при старте делает один запрос
`GET {api}/health`. Если ответа нет (Netlify без функций, GitHub Pages,
просто статика) — работает прежняя схема, ничего не ломается. Это проверено
сквозным тестом `tests/qa/cms-scenarios.test.js` (сценарий 10).

## 3. Слои сервера

```
backend/
├── cli/
│   ├── admin.js          создание/смена пароля, токены восстановления,
│   │                     doctor, stats, audit, unlock
│   └── seed.js           генерация backend/seed.json из каталога витрины
├── netlify/
│   ├── api.mjs           адаптер API под Netlify Functions (+ раздаёт /img/*)
│   └── img.mjs           точка входа функции раздачи фото из Blobs
├── server/
│   ├── config.js         всё из env (+ backend/.env), лимиты, пути, scrypt
│   ├── store.js          JSON-БД: атомарная запись, очередь мутаций,
│   │                     детекция внешней подмены файла, contentRev
│   ├── auth.js           scrypt, timingSafeEqual, сессии, блокировка перебора,
│   │                     лимит по IP, одноразовые токены восстановления
│   ├── sanitize.js       серверный аналог sanitizeDB/esc/safeUrl (белые списки)
│   ├── media.js          multipart, проверка по сигнатуре и структуре файла,
│   │                     публикация в img/, удаление старых и осиротевших
│   ├── content.js        CRUD контента + публикация data.json + ревизии
│   ├── http.js           тело с лимитом, cookie, IP, CSRF, заголовки
│   ├── api.js            маршрутизация (общая для Node и Netlify)
│   ├── audit.js          журнал безопасности NDJSON с вымарыванием секретов
│   └── server.js         HTTP-сервер: API + статика + /img + gzip
├── seed.json             каталог для первого старта (без jsdom в рантайме)
├── .env.example          шаблон переменных окружения
└── package.json          зависимость рантайма ровно одна: busboy
```

Ключевое решение: `api.js` не знает про `req`/`res` Node — он принимает
подготовленный `ctx` и возвращает описание ответа. Поэтому один и тот же
роутер обслуживает и Node-сервер на VPS, и Netlify Functions.

## 4. Поток данных при правке в CMS

```
админ в /admin
   │  (1) меняет поле товара → dbSave()
   ▼
assets/js/store.js :: dbSave()
   │  (2) localStorage — локальный черновик и страховка
   │  (3) dfServerSave() с дебаунсом 250 мс
   ▼
PUT /api/admin/content   [Authorization: Bearer <токен в памяти>, If-Match: <rev>]
   │
   ▼
backend/server/api.js → content.replaceAll()
   │  (4) sanitizeContent(): белые списки полей, лимиты длин, safeUrl()
   │  (5) store.setContent(): очередь мутаций, contentRev++
   │  (6) store.publishDataJson(): tmp → rename (атомарно)
   │  (7) audit.log: событие + ревизия (без секретов)
   ▼
data.json в корне сайта  ──►  витрина любого посетителя
```

Если два админа правят одновременно, второй получит `409 rev-conflict` —
перезаписать чужие правки молча нельзя (сценарий 7 в QA-тестах).

## 5. Поток данных при загрузке фото

```
админ выбирает файлы
   ▼
POST /api/admin/products/:id/photos   (multipart/form-data)
   │
   ▼
media.parseMultipart()          — busboy, лимиты: 8 МБ/файл, 24 МБ/запрос, ≤8 файлов
   │
   ▼
sniffType(buf)                  — формат по БАЙТАМ, а не по заголовку браузера
validateImageStructure(buf)     — JPEG: маркер EOI; PNG: chunk IEND; WebP: RIFF-размер
   │        отклоняются: не-изображения, обрезки, форматы вне белого списка, <16 Б
   ▼
replace=true → driver.removeProduct(id)   ← старые файлы удаляются ДО записи новых
   ▼
driver.put(id, index, buf, ext)           — имя файла генерирует сервер
   │                                         (img/<ID>/<номер>.<ext>),
   ▼                                         клиентское имя игнорируется
content.attachPhotos() → sanitize → publishDataJson
```

Имя файла из формы не используется вовсе: `../../../../evil.php.png`
превращается в `img/<id>/1.png`. Это проверено тестами (media-api, сценарий 3).

## 6. Хранилище: почему JSON-файл, а не SQLite

| Критерий | Решение |
|---|---|
| Зависимости | `better-sqlite3` требует нативной сборки (node-gyp) — на целевом хостинге может не быть toolchain. `node:sqlite` появился только в Node 22 |
| Переносимость | JSON-файл копируется как есть; на VPS, в контейнере, на Netlify — одинаково |
| Целостность | tmp → `fsync` → `rename` + `fsync` каталога: запись атомарна, «половинчатых» состояний нет |
| Гонки | Все мутации идут через одну очередь (`store.update`), чтение — через кэш с отпечатком файла |
| Внешние правки | Отпечаток = размер + mtime + inode + SHA-256 содержимого. Восстановление из бэкапа или ручная правка детектируются и перечитываются |
| Повреждение | Файл копируется в `db.json.corrupt.<ts>`, а учётки и сессии восстанавливаются из последнего валидного кэша — админов не «выбрасывает» |
| Масштаб | Объёма (61 товар, 4 подборки) хватает на годы; замена на Postgres/SQLite — это переписать один модуль `store.js`, API не меняется |

Медиа лежат отдельно (`img/<ID>/`), а не в БД: это снимает лимит
`localStorage`, позволяет отдавать фото с кэшем CDN и удалять их физически.

### 6.1. То же хранилище в serverless (Netlify)

У функций Netlify постоянной файловой системы нет, поэтому `store.js` умеет
работать через подключаемый бэкенд:

```
store.setBackend({ readDB, writeDB })   ← backend/server/store-blobs.js
```

Согласование с синхронным API бэкенда:

1. `hydrate()` — один раз в начале вызова функции читает БД из Blobs в память;
   дальше все чтения синхронны, поэтому остальной код не меняется;
2. каждая мутация пишет в память и ставит запись в очередь;
3. `flush()` — адаптер дожидается очереди **до возврата ответа**. Без этого
   инстанс может быть заморожен сразу после ответа и правка потеряется.

Медиа использует тот же интерфейс драйвера (`put / removeUrl / removeProduct /
list`), что и файловый, поэтому `media.js` не знает, куда именно пишет.
`data.json` в serverless не публикуется (корень публикации только для чтения) —
витрина берёт каталог из `GET /api/content`, а фото отдаёт функция `img.mjs`.

Проверить драйвер на реальной платформе из песочницы нельзя, поэтому в
`store-blobs.js` есть **mock с тем же контрактом** (`get/set/delete/list` c
`prefix` и `cursor`) поверх обычной папки. На нём `tests/backend/netlify-adapter.test.js`
прогоняет адаптер целиком: маршрутизацию, гидратацию, обязательный flush,
bootstrap админа из env, персистентность между «холодными» запусками, раздачу
и удаление медиа. Единственное, что остаётся непроверенным до деплоя, —
поведение самого Netlify (его контекст, лимиты, сборка esbuild).

## 7. Что где хранится

| Данные | Где | Клиент видит? |
|---|---|---|
| Логин, хэш пароля (scrypt), соль | `backend/data/db.json` | **нет**, никогда |
| Токен сессии | в памяти вкладки + httpOnly-кука; в БД — только HMAC-хэш | кука не читается JS |
| CSRF-токен | кука `df-csrf` (без httpOnly — так задумано для double-submit) | да, но он бесполезен без своей сессии |
| Контент (товары, подборки, hero) | БД + публикуемый `data.json` | да — это публичные данные витрины |
| Фото | `img/<ID>/<n>.<ext>` | да |
| Журнал безопасности | `backend/data/audit.log` | только авторизованному админу (`GET /api/admin/audit`) |
| Черновик правок | `localStorage` `df-cms-v1` | да (это браузер админа) |

`backend/data/` закрыт от веба (блокировка в `server.js`, `deploy/serve.js`,
`_redirects`, `.htaccess`, nginx) и исключён из git (`.gitignore`).

## 8. Каталог API

Публичные:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | живость, версия, тип хранилища, режим CMS |
| GET | `/api/content` | каталог витрины (санитизированный) + `rev` + ETag |
| POST | `/api/auth/login` | вход: логин + пароль → токен, кука, CSRF |
| POST | `/api/auth/reset` | смена пароля по одноразовому токену восстановления |

Требуют сессию:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/auth/me` | текущий админ + продление сессии |
| POST | `/api/auth/logout` | уничтожить сессию на сервере |
| GET/PUT | `/api/admin/content` | весь контент; PUT принимает `If-Match: <rev>` |
| GET/PUT/PATCH | `/api/admin/hero` | главный экран |
| GET/PUT/POST | `/api/admin/collections` | подборки |
| PUT/PATCH/DELETE | `/api/admin/collections/:id` | одна подборка |
| GET/POST | `/api/admin/products` | список / создание |
| GET/PATCH/PUT/DELETE | `/api/admin/products/:id` | карточка товара |
| POST | `/api/admin/products/:id/photos` | multipart-загрузка фото (`replace=true|false`) |
| DELETE | `/api/admin/products/:id/photos` | удалить одно фото (по `url` или `index`) |
| POST | `/api/admin/media/orphans` | убрать файлы, на которые никто не ссылается |
| POST | `/api/admin/reset` | вернуться к встроенному каталогу |
| GET/POST | `/api/admin/admins` | список учётку / создать учётку |
| POST | `/api/admin/password` | смена пароля (требует текущий) |
| POST | `/api/admin/recovery-token` | выпустить одноразовый токен восстановления |
| GET | `/api/admin/audit` | последние 300 записей журнала безопасности |

Единый формат ответа: `{ ok: true, … }` или `{ ok: false, error: "<код>" }`.
Коды ошибок намеренно обезличены: `invalid-credentials` не различает
«нет такой учётки» и «неверный пароль».

## 9. Совместимость и что изменилось в клиентском коде

| Файл | Изменение |
|---|---|
| `assets/js/store.js` | добавлен серверный слой (`dfProbeServer`, `dfApiRequest`, `dfServerSave`, `dfUploadPhotos`), `dbSave()` сам синхронизируется с сервером, `dbInit()` получил приоритет: API → `data.json` → `localStorage` → seed |
| `assets/js/fonts.js` | **новый файл**: неблокирующая загрузка шести начертаний с jsdelivr (раньше это были шесть render-blocking `<link>` в `<head>`) |
| `assets/js/admin/admin-main.js` | серверный вход/выход (`dfServerLogin`, `dfServerLogout`), поле логина показывается только в серверном режиме |
| `index.html`, `admin/index.html` | убраны блокирующие ссылки на шрифты, добавлен `<script src="…/fonts.js">` |
| `admin/index.html` | добавлено поле логина (`#loginField`, по умолчанию `hidden`) |

Клиентская CMS (`DFAuth`, вкладки панели, экспорт/импорт) сохранена полностью —
она остаётся рабочим режимом на статическом хостинге.
