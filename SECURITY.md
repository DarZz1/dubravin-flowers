# SECURITY.md — модель угроз и меры защиты

Сайт статический: HTML/CSS/JS раздаются хостингом, бэкенда нет. Это определяет
и возможности, и **пределы** защиты. Ниже честно описано, что защищено, как
именно, и что в принципе не может быть защищено на статическом сайте.

---

## 1. Что сделано

### 1.1 Доступ к CMS (`/admin`)

| Мера | Реализация |
|---|---|
| Панель не видна на витрине | Из футера убрана ссылка; из hash-роутера удалён маршрут `#/admin` (теперь это 404). Код CMS не загружается на витрине вообще |
| Отдельный адрес | `admin/index.html` — физическая страница, открывается по `/admin` на любом хостинге |
| Пароль не хранится открытым | Хэш **PBKDF2-HMAC-SHA256, 260 000 итераций**, случайная соль 16 байт (WebCrypto). Fallback для `file://` — итеративный SHA-256 (100 000 раундов) на собственной реализации, сверенной с `node:crypto` |
| Защита от перебора | После 5 неудач — блокировка 30 с, удвоение за каждую следующую неудачу, потолок 15 минут. Счётчик в localStorage — переживает перезагрузку страницы |
| Timing-атаки | Сравнение хэшей постоянной длительности (`safeEqual`) |
| Сессия | Токен 32 байта из CSPRNG в **sessionStorage** (закрыл вкладку — вышел), таймаут бездействия 30 минут, продление по активности |
| Смена пароля | Вкладка «Данные» → «Безопасность», требует текущий пароль; при смене перевыпускается соль |
| Индексация | `meta robots noindex`, `X-Robots-Tag`, `robots.txt Disallow: /admin/` |
| UI входа | Ошибки выводятся через `textContent` (не `innerHTML`), поля чистятся после входа, `autocomplete="current-password"/"new-password"`, ограничения длины 8–128 |

### 1.2 XSS (межсайтовый скриптинг)

- **Экранирование вывода.** Все данные из БД (названия, описания, состав,
  подборки, id) проходят `esc()` перед попаданием в HTML — и на витрине,
  и в панели. Тосты тоже экранируются.
- **Белые списки URL.** `safeUrl()` пропускает для `src` только относительные
  пути, `http(s)://` и `data:image/*`. `javascript:`, `vbscript:`,
  `data:text/html`, protocol-relative `//evil.com` заменяются на `#`.
- **Санитизация на входе.** `sanitizeDB()` применяется ко всем внешним данным:
  localStorage, `data.json`, импорт файла, storage-события из других вкладок.
  Отсекаются лишние поля, ограничиваются длины (название 160, описание 2000,
  фото ≤12, состав ≤40, товаров ≤2000), id приводятся к `[A-Za-z0-9_-]`,
  цены — к числам, булевы — к `true/false`. Загрязнение `__proto__` невозможно:
  объект собирается заново из белого списка полей.
- **Никаких inline-обработчиков.** `onerror=` у изображений заменены на
  `data-imgfallback` + один capture-обработчик на `document`. Это обязательное
  условие строгой CSP.
- **Проверка в тестах.** Отдельные тесты добавляют в БД `<script>`,
  `<img src=x onerror=…>`, кавычки и `javascript:`-URL и проверяют, что в DOM
  не появляется исполняемых узлов (включая round-trip парсинг сериализованной
  разметки через `DOMParser`).

### 1.3 Content Security Policy

Meta-CSP на обеих страницах (и те же правила в серверных заголовках):

```
default-src 'self';
script-src 'self';                                                  # витрина и /admin
style-src  'self' 'unsafe-inline' https://cdn.jsdelivr.net;
font-src   'self' https://cdn.jsdelivr.net data:;
img-src    'self' data: blob: https:;
connect-src 'self';
object-src 'none'; base-uri 'self'; form-action 'self';
frame-ancestors 'none';   # только в серверных заголовках
```

- `'unsafe-inline'` в `script-src` **нет** — даже при успешной HTML-инъекции
  злоумышленник не сможет выполнить inline-скрипт.
- `'unsafe-inline'` оставлен только для `style-src`: сайт использует
  `style`-атрибуты в шаблонах; скрипты через стили в современных браузерах
  не выполняются.
- `object-src 'none'` закрывает `<object>/<embed>`; `base-uri 'self'` —
  перехват `<base>`; `form-action 'self'` — отправку форм на чужие домены.
- `/admin` не загружает сторонние скрипты вообще (только `'self'`) —
  меньше поверхность атаки и нет зависимости от CDN.

### 1.4 Серверные заголовки

Готовые конфиги для Netlify/Cloudflare (`_headers`), Vercel (`vercel.json`),
Apache (`.htaccess`), nginx (`deploy/nginx.conf.example`) и локального сервера:

- `X-Content-Type-Options: nosniff` — браузер не «угадывает» тип файла;
- `X-Frame-Options: DENY` + `frame-ancestors 'none'` — защита от кликджекинга;
- `Referrer-Policy: strict-origin-when-cross-origin`;
- `Permissions-Policy` — отключены геолокация, микрофон, камера, платежи;
- `Strict-Transport-Security` — принудительный HTTPS (включается на HTTPS);
- `X-Robots-Tag: noindex` для `/admin`;
- редирект `/admin` → `/admin/`.

### 1.5 Прочее

- **Path traversal:** локальный сервер нормализует путь **до** проверок и не
  выходит за корень; скрытые файлы и служебные каталоги
  (`tests`, `deploy`, `build_tools`, `node_modules`, `package*.json`) не
  отдаются. На прод-хостингах эти каталоги блокируют `_redirects`/`.htaccess`/
  nginx — а лучше просто не публиковать их.
- **Внешние ссылки:** все `target="_blank"` имеют `rel="noopener"`.
- **`window.open`** для заказа в VK — только с `noopener`.
- **Нет секретов в коде:** ни паролей, ни ключей, ни предвычисленных хэшей;
  проверяется статическим тестом.
- **Нет обращения к `location.hash/search/href`** вне роутера и boot —
  исключён класс DOM-XSS «прочитал URL → вставил в DOM».
- **Отказоустойчивость библиотек:** GSAP/ScrollTrigger/Lenis лежат локально
  в `assets/js/vendor/` — витрина не зависит от доступности CDN (медленный
  или заблокированный CDN больше не тормозит первую загрузку). Если скрипт
  всё же не выполнился, `config.js` подставляет no-op-шим — витрина работает
  (без анимаций), а не падает.
- **Ключи хранилища** в едином неймспейсе `df-*` — меньше шансов конфликта
  с чужими скриптами на том же домене.

## 2. Честные ограничения статического сайта

Это важно понимать, чтобы не питать ложных надежд:

1. **Клиентская авторизация не является криптостойкой границей.**
   HTML и JS страницы `/admin` отдаются любому посетителю (без бэкенда
   нельзя проверить пароль на сервере). Человек, умеющий открывать DevTools,
   может выполнить `DFAuth` напрямую или подделать сессию **в своём браузере**.
2. **Но взламывать там нечего.** Всё, чем управляет CMS, — это
   `localStorage` **одного** посетителя. Злоумышленник, «обойдя» пароль,
   сможет изменить содержимое только у себя в браузере; на сайт для остальных
   посетителей это не влияет никак. Реальная публикация — это загрузка
   `data.json` на хостинг, а она защищена уже **учётными данными хостинга**,
   а не этим паролем.
3. **Пароль защищает от другого:** случайные посетители и поисковики не
   увидят панель, никто не поменяет контент в **вашем** браузере, пока вы
   отошли от компьютера, и никто не подберёт пароль (PBKDF2 + блокировка
   перебора делают подбор бессмысленным).
4. **Изменения в CMS локальны по своей природе.** Требование «сохраняются
   локально и обновляются на сайте» выполнено буквально: правки мгновенно
   видны в вашем браузере (и в соседних вкладках витрины), а для всех
   посетителей публикуется `data.json` (вкладка «Данные» → «Скачать»).

### Если нужна настоящая защита админки

Добавьте серверный слой (любой вариант):

- **HTTP Basic Auth на `/admin`** в nginx (в `deploy/nginx.conf.example`
  есть закомментированный блок `auth_basic`) или на Netlify (Password
  Protection) — тогда без серверного пароля страница даже не загрузится;
- либо перенесите CMS на бэкенд (Node/PHP + БД), где пароль проверяется
  на сервере, а сессия — подписанный httpOnly-cookie.

Для 99% задач витрины достаточно текущей схемы: приватных данных на клиенте
нет, а контент для всех публикуется только через хостинг.

## 3. Чек-лист перед публикацией

- [ ] Залиты только: `index.html`, `admin/`, `assets/`, `img/`, `robots.txt`,
      конфиги хостинга (`_headers`, `_redirects`, `netlify.toml`,
      `vercel.json`, `.htaccess`).
- [ ] **Не** залиты: `tests/`, `deploy/`, `build_tools/`, `node_modules/`,
      `package*.json`.
- [ ] Сайт работает по **HTTPS** (включите HSTS в заголовках после проверки).
- [ ] Открыли `/admin`, создали стойкий пароль (≥8 символов, лучше 12+),
      записали его.
- [ ] Проверили, что `/admin` не индексируется (robots.txt + noindex).
- [ ] После правок в CMS скачали `data.json` и загрузили в корень сайта.
- [ ] Прогнали `npm test` — все наборы зелёные.
